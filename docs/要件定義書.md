## 0. 本アプリの基本コンセプト(最重要)

> **「ログイン状態を覚えるシークレットウィンドウを、アカウントの数だけ並べたデスクトップアプリ」**

- 各アカウントを **Cookie・ストレージを分離した独立セッション(コンテナ)** で開く。これにより同じ SNS に複数アカウントで**同時ログイン**できる(＝Chrome のシークレットモードの寄せ集めだが、ログインは保持される)。
- 各ペインには **各 SNS の公式 Web ページそのもの** を表示する。投稿・DM・コメント・分析は、ユーザーがその本物の画面で**手動操作**する。
- **公式 API は使用しない。** アプリは「横断表示・素早い切替・入力補助」に徹し、SNS の操作を自動化しない。
- 結果として **利用規約違反・アカウント凍結リスクがほぼ無い**(やっていることは「ブラウザでログインして人が操作する」ものと同じ)。API の有料化・仕様変更にも影響されない。

類似プロダクト: Shift / Ferdium / Wavebox / Stack(マルチサービス・コンテナブラウザ)

## 1. 概要

### 1.1 背景
Instagram・X(旧Twitter)・note・Threads を複数アカウント運用していると、以下の課題が発生する。

- SNS ごと・アカウントごとにブラウザやアプリを切り替える手間が大きい
- 同じブラウザでは複数アカウントに同時ログインできず、ログアウト／再ログインが頻発する
- シークレットウィンドウを使えば同時ログインできるが、閉じるとログインが消え、毎回ログインし直しになる

### 1.2 目的
**複数の SNS・複数アカウントを、ログインを保持したまま 1 つの PC デスクトップアプリ上で同時に開ける** 統合ワークスペースを提供する。各 SNS の本物の画面を横断的に並べ、閲覧・投稿・DM/コメント・分析を 1 アプリ内で完結させる。

### 1.3 プロダクトの一言説明
> 「Instagram・X・note・Threads の全アカウントを、ログインしたまま 1 画面に並べて開けるデスクトップアプリ」

## 2. スコープ

### 2.1 対象 SNS(初期対応)
いずれも「公式 Web ページをコンテナで開く」方式のため、対応の追加は比較的容易。

| SNS | 表示 URL(例) | 備考 |
| --- | --- | --- |
| X (Twitter) | x.com | 予約投稿など純正機能も画面内で利用可 |
| Instagram | instagram.com | PC Web から投稿・DM 可 |
| Threads | threads.net | — |
| note | note.com | 公式 API 不要、Web で投稿・閲覧 |

### 2.2 採用アーキテクチャ(確定方針)
- **方式A:ログインセッション並列型(API 不使用)** を採用する。
- 1 アカウント = 1 独立セッション(パーティション)。各 SNS 公式 Web を内蔵ブラウザ領域(WebView)で表示する。
- アプリ自身は SNS を自動操作しない。できるのは「表示・レイアウト・切替・ローカルな入力補助」まで。

### 2.3 スコープ外(初期リリースでは対象外)
- 公式 API を用いた自動投稿・自動取得・自動集計
- 複数アカウントをまたぐ「統合通知」「統合インボックス」「横断分析ダッシュボード」の**自動集計**(本方式では各 SNS の画面を読む必要があり、規約・技術リスクが高いため原則行わない)
- 上記以外の SNS(Facebook / TikTok / YouTube / LinkedIn 等)
- チーム複数人での同時編集・承認ワークフロー
- スマホ(iOS/Android)ネイティブアプリ

## 3. 想定ユーザー

| ペルソナ | 概要 | 主なニーズ |
| --- | --- | --- |
| 個人の複数アカウント運用者 | 本名垢・趣味垢・副業垢などを使い分ける個人 | アカウント切替なしで一覧したい |
| インフルエンサー / クリエイター | 複数 SNS で発信 | まとめて開いて反応チェック・投稿したい |
| SNS 運用担当者 / マーケター | 複数ブランド・クライアントのアカウント管理 | ログインし直しの手間なく一元管理したい |

## 4. 用語定義
| 用語 | 定義 |
| --- | --- |
| アカウント | 各 SNS における 1 つのログインユーザー |
| サービス | Instagram / X / note / Threads 等の SNS 種別 |
| コンテナ(セッション) | Cookie・ストレージを分離した独立ログイン領域。1 アカウント = 1 コンテナ |
| ペイン | 画面上で 1 アカウント(1 コンテナ)を表示する領域 |
| ワークスペース | ペインの配置・組み合わせを保存したレイアウト |

## 5. 機能要件

> 本方式では「アプリが自動でやる」のではなく「各 SNS の本物の画面でユーザーが操作し、アプリはそれを並べて補助する」。各要件の実現手段をこの前提で記載する。

### 5.1 アカウント管理(コア)
| ID | 要件 | 優先度 |
| --- | --- | :---: |
| FR-A-01 | SNS 種別とアカウントを追加・編集・削除できる | 必須 |
| FR-A-02 | **1 アカウント = 1 独立セッション**で管理し、同一 SNS の複数アカウントに同時ログイン状態を維持できる | 必須 |
| FR-A-03 | **アプリ再起動後もログインを保持**する(シークレットと違い消えない) | 必須 |
| FR-A-04 | アカウントにラベル・色・アイコン・グループ(例: クライアント別)を付与できる | 高 |
| FR-A-05 | アカウント一覧をサイドバーで表示し、クリックで該当ペインへ切替・フォーカスできる | 必須 |
| FR-A-06 | アカウント単位でセッションを破棄(ログアウト相当・データ削除)できる | 高 |

### 5.2 同時表示 / レイアウト(コア)
| ID | 要件 | 優先度 |
| --- | --- | :---: |
| FR-L-01 | 複数アカウントを**同時に**画面分割(マルチペイン/マルチカラム)で表示できる | 必須 |
| FR-L-02 | 「タブ表示(1枚ずつ)」と「グリッド表示(2x2 / 3カラム等)」を切り替えられる | 高 |
| FR-L-03 | ペインのサイズ変更・並べ替え・表示/非表示ができる | 中 |
| FR-L-04 | レイアウトを「ワークスペース」として保存し、用途別に呼び出せる | 中 |
| FR-L-05 | 各ペインを個別にリロード・進む/戻る・ホームへ移動できる | 高 |
| FR-L-06 | 非表示/非アクティブなペインをスリープさせ、メモリ/CPU を節約できる | 高 |

### 5.3 閲覧・モニタリング
| ID | 要件 | 実現手段 | 優先度 |
| --- | --- | --- | :---: |
| FR-V-01 | 各アカウントのタイムライン/フィードを閲覧できる | 各ペインで公式 Web を表示 | 必須 |
| FR-V-02 | 新着の気配をサイドバーのバッジ等で知らせる | ページタイトル/favicon の変化を検知する程度の軽量な補助(ページ内容の解析はしない) | 中 |
| FR-V-03 | 複数ペインを並べて「見る」こと自体でモニタリングを成立させる | レイアウト機能で担保 | 必須 |

> ※ 複数垢を横断した「統合通知一覧」は本方式では原則提供しない(各ページの解析が必要になり規約・保守リスクが高いため)。

### 5.4 投稿 / 予約投稿
| ID | 要件 | 実現手段 | 優先度 |
| --- | --- | --- | :---: |
| FR-P-01 | 各アカウントで投稿できる | 各ペインの公式投稿画面で手動投稿 | 必須 |
| FR-P-02 | **予約投稿** | **各 SNS の純正の予約投稿機能**(X・Instagram 等が Web で提供)を各ペインで利用 | 高 |
| FR-P-03 | 投稿文の下書き・テンプレートをアプリ内に保存し、コピー/貼り付けで各ペインに流用できる(入力補助) | ローカル保存 + クリップボード連携 | 中 |
| FR-P-04 | 「同じ文面を複数アカウントに投稿」する作業を補助する(各ペインの投稿画面を順に開く＋下書きを呼び出す)。自動入力・自動送信はしない | 投稿ガイド/クイック起動 | 中 |

> ※ アプリが自動でクロスポスト・自動送信することはしない(自動操作は規約・凍結リスクがあるため)。あくまで「開く・貼る」をラクにする補助に留める。

### 5.5 DM / コメント対応
| ID | 要件 | 実現手段 | 優先度 |
| --- | --- | --- | :---: |
| FR-M-01 | 各アカウントの DM / コメントに返信できる | 各ペインの公式画面で手動対応 | 必須 |
| FR-M-02 | 返信定型文(スニペット)をアプリ内に登録し、貼り付けで使える | ローカル保存 + クリップボード連携 | 中 |

> ※ 複数垢を束ねた「統合インボックス」は本方式では提供しない。

### 5.6 分析 / レポート
| ID | 要件 | 実現手段 | 優先度 |
| --- | --- | --- | :---: |
| FR-R-01 | 各アカウントのインサイト/アナリティクスを確認できる | 各 SNS 純正のアナリティクス画面をペインで開く(ショートカット登録) | 中 |
| FR-R-02 | よく見る分析ページへワンクリックで飛べるブックマークを持てる | ローカル保存 | 低 |

> ※ 横断的な自動集計ダッシュボードは本方式では提供しない。

### 5.7 共通機能
| ID | 要件 | 優先度 |
| --- | --- | :---: |
| FR-C-01 | キーボードショートカットでアカウント/ペインを切替できる | 中 |
| FR-C-02 | アプリ全体のダークモード / ライトモード | 中 |
| FR-C-03 | 各ペインのズーム(表示倍率)調整 | 低 |
| FR-C-04 | 多言語対応(初期は日本語) | 低 |
| FR-C-05 | アプリ自動アップデート | 中 |
| FR-C-06 | 広告ブロック/トラッキング抑止(任意、動作安定と軽量化のため) | 低 |

## 6. 非機能要件

### 6.1 性能
- 10 アカウント程度を同時表示しても実用的に動作すること(目安)
- WebView は非表示時にスリープ(リソース解放)させ、メモリ肥大を防ぐ(FR-L-06)

### 6.2 セキュリティ / プライバシー
| ID | 要件 |
| --- | --- |
| NFR-S-01 | ログイン Cookie・セッションは各コンテナ内に分離保存し、相互に漏れないこと |
| NFR-S-02 | セッションデータはユーザーのローカル端末に保存し、無断で外部送信しないこと |
| NFR-S-03 | アプリ起動時のマスターパスワード/生体認証ロック(任意) |
| NFR-S-04 | アカウント削除時にそのコンテナの Cookie・キャッシュ・ストレージを完全に消去できること |

### 6.3 可用性・信頼性
- SNS 側の UI 変更・障害時も、該当ペインのみ影響が留まり他ペインに波及しないこと
- 本方式は SNS のページ構造に依存しない(ページを解析しない)ため、UI 変更への耐性が高い

### 6.4 拡張性・保守性
- SNS は「URL + アイコン + 設定」の登録で追加できる構成とし、新 SNS 対応を容易にする
- ユーザーが任意の Web サービス(他 SNS 等)を自分で追加できる余地を持たせる

## 7. 技術構成(案)
> 確定ではなく初期の技術方針。詳細は設計フェーズで決定。

| 層 | 技術候補 | 備考 |
| --- | --- | --- |
| アプリ基盤 | Electron / Tauri | **アカウント単位のセッション分離**に対応できることが選定の最重要条件 |
| セッション分離 | Electron の `session.fromPartition('persist:acc-xxx')` / `<webview>` partition 等 | 「persist:」付きで**ログインを永続化**(＝消えないシークレット) |
| UI | React + TypeScript | サイドバー・レイアウト・ペイン管理 |
| ローカル保存 | SQLite / ファイル | アカウント設定・ワークスペース・下書き・定型文 |
| 認証情報 | 各コンテナが自身の Cookie を保持(アプリ側で生パスワードは扱わない) | ユーザーは各 SNS 画面で直接ログインする |

> **補足:** 本方式では「アプリが SNS の API キーやパスワードを預かる」ことがない。ユーザーは各ペイン内で普段どおりログインするだけで、認証情報はそのコンテナの Cookie として OS 管理下に保存される。

## 8. 規約・リスクの考え方(本方式の優位点)

本アプリの中核は「ブラウザでログインして人が操作する」ことであり、以下のリスクを**原則回避**できる。

| リスク | 本方式での扱い |
| --- | --- |
| API 有料化・仕様変更(特に X) | **影響なし**(API を使わない) |
| 自動操作・スクレイピングによる規約違反・凍結 | **原則回避**(自動操作しない。入力補助はユーザー操作の範囲内) |
| 各 SNS の UI 変更による機能破綻 | **耐性が高い**(ページ構造に依存しない) |

ただし以下は留意する。

- 各 SNS の利用規約で「サードパーティブラウザ/クライアントでの利用」自体が制限されるケースは稀にあるため、公式 Web をそのまま表示する方針を守る(独自改変・自動操作をしない)。
- 「複数アカウント運用」そのものが各 SNS の規約で制限される場合がある(別人になりすます等)。これはアプリではなくユーザーの運用責任であることを明示する。
- WebView の埋め込みを嫌うサイトが将来現れた場合に備え、外部ブラウザで開くフォールバックを用意する。

## 10. 開発フェーズ / MVP

| フェーズ | 内容 | 含む主要要件 |
| --- | --- | --- |
| **MVP(Phase 1)** | アカウント追加 → 独立セッションで公式 Web を開く → ログイン保持 → 1枚ずつタブ表示 | FR-A-01〜06, FR-L-05, NFR-S-01/02/04 |

> まずは Phase 1「複数アカウントをログイン保持したまま開ける」だけでも、現状の最大の不満(ログインし直し地獄)が解消する。ここを最小動作版として最優先する。

## 11. 前提・制約・未決事項

### 前提
- ユーザーは各 SNS の正規アカウントを保有し、各ペイン内で自らログインする
- 利用は各 SNS の利用規約の範囲内で、ユーザー責任で行う

### 未決事項(要確認)
1. 対応 OS の優先順位(Windows 優先 / macOS 優先 / 両方)
2. 基盤の選定(Electron:実績豊富で WebView 分離が容易 / Tauri:軽量だが WebView 分離の実装難度を要検証)
3. 「入力補助(下書き共有・クイック起動)」をどこまで作り込むか(MVP では無しでも成立する)
4. ユーザーが任意の Web サービスを自由に追加できるようにするか(汎用コンテナブラウザ化するか)
5. 配布・収益化(買い切り / サブスク / 無料・OSS)
6. アプリ名・ブランド
