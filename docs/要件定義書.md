## 1. 概要

### 1.1 背景
Instagram・X(旧Twitter)・note・Threads を複数アカウント運用していると、以下の課題が発生する。

- SNS ごと・アカウントごとにブラウザやアプリを切り替える手間が大きい
- 同じブラウザでは複数アカウントに同時ログインできず、ログアウト／再ログインが頻発する
- 投稿・DM・コメント対応・分析が各サービスに分散し、運用が煩雑

### 1.2 目的
**複数の SNS・複数アカウントを 1 つの PC デスクトップアプリ上で同時に開き、横断的に「閲覧・投稿・DM/コメント対応・分析」まで行える** 統合ワークスペースを提供する。

### 1.3 プロダクトの一言説明
> 「Instagram・X・note・Threads の全アカウントを、1 画面で同時に開いて運用できるデスクトップアプリ」

## 2. スコープ

### 2.1 対象 SNS(初期対応)
| SNS | 閲覧 | 投稿 | DM/コメント | 分析 | 備考 |
| --- | :---: | :---: | :---: | :---: | --- |
| X (Twitter) | ○ | ○ | ○ | ○ | API 有料化の影響大(後述) |
| Instagram | ○ | ○ | ○ | ○ | 主にビジネス/クリエイターアカウント向け API |
| Threads | ○ | ○ | △ | △ | 公式 API は発展途上 |
| note | ○ | ○ | △ | △ | 公式 API が公開されていない(後述) |

### 2.2 アプリ形態
- **PC デスクトップアプリ**(Windows / macOS を想定、将来 Linux も視野)
- 各 SNS の公式 Web を **アカウントごとに独立したセッション(コンテナ)** で読み込み、同一画面に並べて表示するアプローチを基本とする
- 公式 API が利用可能なサービス・機能については API を併用する

### 2.3 スコープ外(初期リリースでは対象外)
- Facebook / TikTok / YouTube / LinkedIn など上記以外の SNS
- チーム複数人での同時編集・承認ワークフロー(将来検討)
- スマホ(iOS/Android)ネイティブアプリ
- 広告出稿管理

## 3. 想定ユーザー

| ペルソナ | 概要 | 主なニーズ |
| --- | --- | --- |
| 個人の複数アカウント運用者 | 本名垢・趣味垢・副業垢などを使い分ける個人 | アカウント切替なしで一覧したい |
| インフルエンサー / クリエイター | 複数 SNS で発信 | まとめて投稿・反応チェックしたい |
| SNS 運用担当者 / マーケター | 複数ブランド・クライアントのアカウント管理 | 投稿予約・DM対応・分析を一元化したい |

## 4. 用語定義
| 用語 | 定義 |
| --- | --- |
| アカウント | 各 SNS における 1 つのログインユーザー |
| サービス | Instagram / X / note / Threads 等の SNS 種別 |
| コンテナ(セッション) | Cookie・ストレージを分離した独立ログイン領域。1 アカウント = 1 コンテナ |
| ペイン | 画面上で 1 アカウントを表示する分割領域 |
| 統合インボックス | 複数アカウントの DM・コメントをまとめた受信箱 |
| 統合タイムライン | 複数アカウントの投稿・通知をまとめた一覧 |

## 5. 機能要件

### 5.1 アカウント管理
| ID | 要件 | 優先度 |
| --- | --- | :---: |
| FR-A-01 | SNS 種別とアカウントを追加・編集・削除できる | 必須 |
| FR-A-02 | 1 アカウント = 1 独立セッション(Cookie/ストレージ分離)で管理し、同一 SNS の複数アカウントに同時ログイン状態を維持できる | 必須 |
| FR-A-03 | アカウントにラベル・色・アイコン・グループ(例: クライアント別)を付与できる | 高 |
| FR-A-04 | アカウント一覧をサイドバーで表示し、クリックで該当ペインへフォーカスできる | 必須 |
| FR-A-05 | 各アカウントのログイン状態・未読件数をサイドバーにバッジ表示する | 高 |
| FR-A-06 | アプリ再起動後もログインセッションを保持する(再ログイン不要) | 必須 |

### 5.2 同時表示 / レイアウト
| ID | 要件 | 優先度 |
| --- | --- | :---: |
| FR-L-01 | 複数アカウントを**同時に**画面分割(マルチペイン/マルチカラム)で表示できる | 必須 |
| FR-L-02 | タブ表示とグリッド(2x2 / 3カラム等)表示を切り替えられる | 高 |
| FR-L-03 | ペインのサイズ変更・並べ替え・表示/非表示ができる | 中 |
| FR-L-04 | レイアウトを「ワークスペース」として保存し、用途別に呼び出せる | 中 |
| FR-L-05 | 各ペインを個別にリロード・進む/戻る操作できる | 高 |

### 5.3 閲覧・モニタリング
| ID | 要件 | 優先度 |
| --- | --- | :---: |
| FR-V-01 | 各アカウントのタイムライン/フィードを閲覧できる | 必須 |
| FR-V-02 | 複数アカウントの通知をまとめた**統合通知一覧**を表示できる | 高 |
| FR-V-03 | 新着通知をアプリ/OS 通知で知らせる(アカウント単位で ON/OFF) | 高 |
| FR-V-04 | キーワード・ハッシュタグのモニタリング(エゴサーチ)ができる | 中 |

### 5.4 投稿 / 予約投稿
| ID | 要件 | 優先度 |
| --- | --- | :---: |
| FR-P-01 | テキスト・画像・動画を含む投稿を作成できる | 必須 |
| FR-P-02 | 1 つの投稿を**複数アカウント・複数 SNS へ同時投稿(クロスポスト)**できる | 高 |
| FR-P-03 | 日時を指定した**予約投稿**ができる | 高 |
| FR-P-04 | 下書き保存・テンプレート化ができる | 中 |
| FR-P-05 | SNS ごとの文字数制限・画像仕様をリアルタイムに検証・警告する | 高 |
| FR-P-06 | 投稿前プレビュー(各 SNS の見え方)を表示する | 中 |
| FR-P-07 | 予約投稿のカレンダー表示・一覧管理ができる | 中 |

### 5.5 DM / コメント対応
| ID | 要件 | 優先度 |
| --- | --- | :---: |
| FR-M-01 | 複数アカウントの DM を**統合インボックス**で確認・返信できる | 高 |
| FR-M-02 | 投稿へのコメント/リプライを一覧し返信できる | 高 |
| FR-M-03 | 対応済み/未対応のステータス管理ができる | 中 |
| FR-M-04 | 定型文(返信テンプレート)を登録・挿入できる | 中 |

### 5.6 分析 / レポート
| ID | 要件 | 優先度 |
| --- | --- | :---: |

## 6. 非機能要件

### 6.1 性能
- 10 アカウント程度を同時表示しても実用的に動作すること(目安)
- 各ペインはメモリ使用量を考慮し、非表示ペインのスリープ(リソース解放)に対応する

### 6.2 セキュリティ / プライバシー
| ID | 要件 |
| --- | --- |
| NFR-S-01 | ログイン認証情報・トークンは OS のセキュアストレージ(Keychain / Credential Manager 等)または暗号化して保存する |
| NFR-S-02 | アカウントデータはユーザーのローカル端末に保存し、無断で外部送信しない |
| NFR-S-03 | 各アカウントのセッションは完全分離し、Cookie・キャッシュの混在を防ぐ |
| NFR-S-04 | アプリ起動時のマスターパスワード/生体認証ロック(任意) |

### 6.3 可用性・信頼性
- SNS 側の UI 変更・障害時に、該当ペインのみ影響が留まり他に波及しないこと
- 予約投稿はアプリ起動中に実行(常駐/バックグラウンド動作の要否は要検討 → 未決事項)

### 6.4 拡張性・保守性
- SNS を「プラグイン(アダプタ)」単位で追加できる設計
- API 版 / Web 版の 2 系統を切り替え可能なアーキテクチャ

## 8. 各 SNS の制約・リスク(**重要**)

本アプリの中核である「複数アカウント同時ログイン」「自動投稿」は、各 SNS の利用規約・技術制約の影響を強く受ける。実装前に必ず最新の規約・API 仕様を確認すること。

| SNS | 主な制約・リスク |
| --- | --- |
| **X (Twitter)** | 公式 API が有料化・機能制限。無料枠では投稿取得等が大きく制限される。Web 自動操作は規約違反となる可能性があり、アカウント凍結リスクがある |
| **Instagram** | 投稿・インサイト取得は原則 Graph API(ビジネス/クリエイターアカウント + Facebook連携)が必要。個人アカウントでできる操作は限定的。自動化はレート制限と規約の制約が厳しい |
| **Threads** | 公式 API(Threads API)は提供が始まったが機能が限定的。仕様変更が頻繁 |
| **note** | 公開された公式 API が存在しない。Web 表示・手動投稿が中心となり、自動投稿・取得は技術的・規約的リスクが高い |

> **方針**: 規約に抵触しない範囲での実装を基本とする。公式 API がある機能は API を優先し、無い機能は「ユーザー自身の操作を補助する(同時表示・下書き補助)」範囲に留める。自動化機能はアカウント凍結リスクをユーザーに明示する。

## 11. 前提・制約・未決事項

### 前提
- ユーザーは各 SNS の正規アカウントを保有している
- 利用は各 SNS の利用規約の範囲内で行う

### 未決事項(要確認)
1. 対応 OS の優先順位(Windows 優先 / macOS 優先 / 両方)
2. 予約投稿のためにアプリ常駐・バックグラウンド動作を許容するか(端末起動が必要か、クラウド実行が必要か)
3. チーム利用(複数人・権限管理)の有無 ― 将来対応か初期対応か
4. API 課金(特に X)が発生する機能をどこまで含めるか
5. 収益化・配布形態(買い切り / サブスク / 無料)
6. 対応言語の範囲
